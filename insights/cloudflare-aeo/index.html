Cloudflareが「順位」から「AI推薦」へ：企業サイトは何を変えるべきか

Cloudflareの提言は、検索順位だけでなくAIが企業を理解・比較・推薦できる状態を整える重要性を示しています。robots.txtや構造化データ等の技術対応だけでは完結しません。企業情報の一貫性、比較可能性、推薦根拠、行動導線まで含めて見る必要があります。

何が起きたか

2026年8月6日、Cloudflareは公式ブログで、Agent Readiness ダッシュボードへの統合と Answer Engine Optimization（AEO） 向けの可視化機能を紹介しました。テーマは「From ranking to recommended」——検索順位の時代から、AIアシスタントやエージェントに推薦される時代への移行です。

Cloudflareは、HTMLページリクエストの半数未満が人間由来になり、エージェント向けトラフィックが増えていると述べています。従来のクリック数やページビューだけでは、AIがサイトをどう読み、どう引用しているかが見えにくい——という問題意識が背景にあります。

なぜ「ranking → recommended」が重要なのか

従来の検索最適化は、検索結果ページで見つかり、クリックされることに焦点が当たっていました。AI検索やアシスタント経由の発見では、ユーザーが一覧を自分で比較する前に、エージェントが候補を理解し、比較し、推薦する場面が増えます。

検索とAI推薦の違い

  • 検索：結果一覧に載る（順位・クリック）
  • AI：候補として理解される → 比較される → 推薦される →（場合によっては）行動につながる

Cloudflareが強調するのは、後者の連鎖——特に「推薦される」段階——です。これはAI検索が変える比較の意味や推薦の組み立て方で整理してきた論点と接続します。順位だけを追っても、推薦のロジックまではカバーできません。

Cloudflareが示しているポイント

以下はCloudflare公式ブログに基づく要点です。ARIの解釈と混同しないよう、事実として整理します。

  • Agent Readiness Diagnostics：エージェントがサイトを読む方法（robots.txt、sitemap、HTTPヘッダー、Markdown版、ツール用メタデータ等）でサイトをスキャンし、pass / fail / neutral と根拠を返す。
  • AEOタブ：カテゴリ内の質問でAIアシスタント（Anthropic Claude、OpenAI GPT）が自社を推薦するかをプローブする。検索順位のような単一指標ではない。
  • AI Operator Activity：OpenAIやGoogleなど、主要オペレーター由来のクロール・リファラルトラフィックを可視化する。
  • カテゴリベンチマーク：サイトから業界・カテゴリを推定し、横断的なベンチマークと比較する。
  • early access：AEO Visibility はダッシュボードからリクエストする形（一般提供の範囲は公式情報に依存）。

ARIではどう読むか

Cloudflareは、エージェントのアクセシビリティ（読み取り可能性）、オペレーター由来トラフィックの可視化、カテゴリ内での推薦可視性（AEO）まで、計測と改善の射程を広げています。競合比較ではなく、インフラ事業者としての役割分担です。

Agent Readiness（ARI）は、同じ現象をBusiness / Recommendation Readinessとして読みます——DiscoveryからActionまでを横断し、「企業としてどこを改善すべきか」を判断する視点です。フレームワークは次の五段階で整理できます。

  • Discovery：AIやエージェントに見つけられ、読めるか。DiagnosticsやOperator Activityはここに効く。
  • Understanding：一つの企業として理解されるか。名称・所在地・提供内容の一貫性が鍵。
  • Comparison：カテゴリ内で比較可能な属性があるか。料金・条件・営業時間など。
  • Recommendation：推薦理由を形成できる根拠があるか。AEOプローブが測るのは主にこの層。
  • Action：推薦の先に予約・問い合わせ・購入へ進めるか。

Cloudflareの「ranking → recommended」は、DiscoveryとRecommendationの間にUnderstanding / Comparisonがあることを暗に示しています。技術的な読み取り可能性だけでは、推薦まで到達しない——というのがARIの読み方です。Frameworkで三柱（Visibility・Authority・Actionability）との対応も確認できます。

企業が今確認すべきこと

  • AIやエージェントから、公式の企業情報が見つかるか
  • サイト・地図・FAQ・外部掲載で、会社情報が一貫しているか
  • 比較に必要な事実（料金、条件、エリア、提供内容）がページ上で完結しているか
  • 推薦理由を形成できる根拠（実績、資格、レビュー、第三者情報）があるか
  • 推薦後に予約・問い合わせ・購入へ進める導線があるか

CloudflareのDiagnosticsやAEOは、主にDiscoveryからRecommendation層の可視化と点検に効きます。一方、一貫性や比較情報、行動導線はダッシュボードだけでは自動修正されません——ここがARIが補完する領域です。

技術対応だけでは足りない理由

robots.txt、sitemap、構造化データ、llms.txt、API、MCP——これらはAIにとって重要なシグナルです。3ファイルの役割や推薦の根拠で述べてきたように、入口の整備は必要です。

ただし、シグナルが揃っても、内容が矛盾していればUnderstandingは失敗します。比較属性が欠けていればComparisonは止まります。推薦のあと実行できなければActionは完結しません。Cloudflare自身も、エージェントを「コアユーザーベース」として扱い、見つけやすく・読みやすく・信頼できるサイトが推薦されやすい——と述べており、技術とコンテンツ・信頼の両方を示唆しています。

今すぐ対応するべきか

NOW（優先して確認）

  • 企業情報の一貫性（名称・所在地・提供内容）
  • 比較に使われる基本属性の明示
  • 予約・問い合わせ・購入の行動導線

NEXT（計画的に整備）

  • machine readability（Markdown版、構造化データ、FAQ設計）
  • AI Operator / クロール状況の可視化（Cloudflare利用時はダッシュボード、それ以外はログ分析）
  • カテゴリ内の代表質問に対する推薦状況の定点観測

WATCH（動向を追う）

  • AEO Visibility の一般提供範囲とプローブ仕様の更新
  • エージェント向けツールインターフェース（API / MCP）の業界標準化

Cloudflareの記事は「SEO終了」ではなく、計測対象と最適化の重心が移る——という論旨です。ARIも同様に、SEOを否定するのではなく、推薦と実行まで含めた設計が必要だと読みます。なぜAgent Readinessが基準になるかも参照してください。

ARI Researchとの接続

Research Hubでは、複数AI・複数業種での推薦と引用の実態を定点観測しています。CloudflareのAEOがプローブする「カテゴリ内推薦」と、ARI Researchの「代表質問への回答」は、観測単位は異なれど、Recommendation層の可視化という点で方向性が近いです。

数字やランキングを記事に無理に載せる必要はありません。自社の業種・地域・提供内容に合わせ、ResearchやEvidence Libraryの方法論を参照しながら、定点観測を設計する——それがARI流の読み方です。

自社にとって何を意味するか

Cloudflareの提言が自社にどこまで関係するかは、現在どの段階で止まっているかによって変わります。Discoveryで止まっているのか、Comparisonで脱落しているのか、RecommendationはあるがActionで失敗しているのか——止まりどころが違えば、優先すべき施策も変わります。

一般的なAI検索対策のチェックリストをなぞるだけでは、自社のボトルネックは特定できません。SEO・GEO・Agent Readinessの役割分担を踏まえ、段階ごとにKPIを分けて見ることが出発点になります。
